# ICEcore 工作区规范错误与经验总结

Last updated: 2026-09-27

本文是 ICEcore 的规范错误、用户纠正和可复用经验的唯一记录入口。目标不是保存开发流水账，而是把已发生问题转化为下一次任务开始前可见、执行时可检查、结束时可验证的防线。

## 生效中的防复发规则

- 种子袋作物每日生长兼容必须同时检查随机刻拦截、每日分支覆盖、多格结构与 age=0 首次推进；不能只接入种植入口或以青柠恢复随机刻绕过每日系统。修改外部基类调用前核对传递接口依赖，优先包外桥接避免非必要可选类型链接；见 ERR-20261015-01。

- 本项目规则只从根目录 `AGENTS.md` 与 `docs/INDEX.md` 路由的本地正文读取；文档维护完成前检查规则引用、索引及快照，必要要求必须有本地承载，不新增工作区外规则依赖。见 ERR-20261010-01。
- 客户端内存诊断先核对 JVM 标志：`PerfDisableSharedMem` 会阻断 jstat，优先使用 jcmd。先取 heap_info 和包含垃圾的对象直方图，存活对象统计会触发 GC，必须提前说明暂停影响；不得把堆上限、提交、驻留或包含垃圾的对象数量混为一谈。日志输出前排除完整启动参数行，截图必须确认画面确属目标窗口；规则文档先读标题和生效节，不全文输出大文件。见 ERR-20261005-01。

- KubeJS 新增/迁移事件脚本必须先核对目标 JAR 的事件签名、绑定脚本类型、首次注册时机与 Java 类过滤规则；环境/模组查询优先使用内置 Platform，分支声明与跨脚本回调需用目标 Rhino 实际解释执行；2001.6.5 的 ForgeEvents 仅在 startup_scripts 提供，客户端行为通过受物理客户端保护的启动事件转发（见 ERR-20260821-01）。

- 2026-10-02 时间加速种植兼容复发：旧 `ServerLevelRandomTickMixin` 在 0.01 倍率分支额外乘以 20，并保留每区块周期性控制台输出；同时 `RandomTickScalingTest` 只覆盖减速倍率，文档公式/上限与实现不一致。Forge 47.4.10 字节码确认作物生长、耕地湿度和流体均由 `ServerLevel.tickChunk` 的随机刻抽样触发，经验系数会造成不可预测密度与高频负载，旧测试也无法捕获加速回归。已改为 `RandomTickScaling` 的统一 `ceil((m-1)*base)` / `ceil((1/m-1)*base)` 公式，0.01 倍率合计 100 倍；补偿同时执行方块和流体随机刻，单区块 tick 上限 10000，移除周期性控制台日志，并新增 0.01/0.5/1/10/上限测试。防复发措施：以后修改时间倍率必须先以目标 Forge `tickChunk` 字节码核对随机刻入口，数学规则集中到纯逻辑类并覆盖倍率两侧、边界和上限，文档公式与测试必须同批更新。验证：`gradlew.bat test --tests com.yinfires.icecore.time.RandomTickScalingTest`、`gradlew.bat compileJava`；适用边界：仅覆盖 ICEcore 对主世界随机刻的时间倍率补偿，不改变其它维度或 `doDaylightCycle=false` 行为。状态：已修正，客户端实机种植/干涸回归待用户授权。

- 2026-10-01 种子袋嵌套完整物品渲染（历史经验，2026-10-02 已由产品决策废止）：此前为“普通袋体内嵌完整作物 ItemStack”多次修正 Forge 模型包装、BEWLR 入口和两层 ItemRenderer 坐标补偿。用户现明确改为每个种子袋提供一张完整专用贴图，不再需要程序叠加；相关 `SeedBagRenderer`、`SeedBagBakedModel`、`SeedBagClientModels`、客户端扩展入口、显示参数和公共袋体贴图已全部删除。当前防线改为：每个种子袋必须是独立 `minecraft:item/generated` 模型并直接引用自己的单层贴图；2026-10-08 已接入用户提供的全部 19 张透明 16×16 专用贴图，正式模型统一引用 `icecore:item/<作物ID>_seed_bag`，不得重新引入运行时第二次物品渲染。`SeedBagRenderingContractTest` 固定检查普通模型、本地专用贴图引用与文件存在、旧叠加链完全不存在；素材替换同时检查源文件与资源 SHA-256 一致，并核对 Jade 复用相同种子袋 ItemStack 模型。适用边界：ICEcore 种子袋当前产品方案；若未来另有功能明确要求嵌套完整 ItemStack，应重新评估而不能沿用本条的禁止范围。

- 2026-09-27：普通 Gradle JUnit 进程不能直接通过构造 `ItemStack(Items.*)` 验证原版物品行为；未引导时会抛出 `Not bootstrapped`，仅调用 `Bootstrap.bootStrap()` 又会因测试环境未设置游戏版本而在 DataFixers 初始化时报 `Game version not set`。需要完整 Minecraft 注册表/版本引导的行为应使用 GameTest、运行环境测试或已有可控夹具；普通 JUnit 改为测试不依赖引导的纯逻辑，或对已由真实 Forge 47.4.10 API 核验的调用点建立源码契约门禁，不得为了测试手动拼装不完整的全局引导状态。验证方法：`FoodConsumptionRulesTest` 不加载 `Items`/`ItemStack` 静态注册表，固定检查动态 `getFoodProperties`、事件范围与网络同步，完整 `gradlew.bat test` 和 `clean build` 通过。适用边界：只限制普通 JUnit；具备完整游戏测试引导的环境仍可做真实物品行为测试。

- 2026-09-26：烤炉实现测试曾硬编码目标客户端 KubeJS 临时脚本的旧输入物品 `kaleidoscope_fragrantorchard:juicer`，而脚本已改为 `farmersdelight:wheat_dough`，导致 `OvenImplementationTest` 在环境依赖断言处失败。根因是仓库测试读取工作区外可变脚本并锁定过时内容；影响是完整构建被无关的本地整合包状态阻断。已移除该外部配方测试，仅保留源码结构测试；后续不得把客户端目录临时脚本内容作为仓库单元测试前置条件。验证方法：执行 `gradlew.bat test --tests com.yinfires.icecore.oven.OvenImplementationTest`，确认剩余测试通过。适用边界：需要验证客户端脚本时应使用独立的脚本语法/资源检查，不纳入模组源码单元测试。

以下规则对所有后续任务生效：

- GUI 美术交付执行 `texture-and-model-workflow.md`“参考转化与视觉质量门禁”：以真实消费端偏移合成空/满与首中末选中状态，验证可见 alpha 边界、内容区和连续边缘；参考特征必须与成品可见对应，不以换色、生成调用或打包成功代替视觉验收。

- 模型/UV 交付必须验证贴图依赖、内嵌纹理、预期元素数量、可见面 UV，并在空项目重新导入和检查截图；不得仅凭文件存在或命令退出报告完成。已知本地 MCP 地址须实际握手与只读调用，不以工具列表缺席推断不可用。

1. 开工必须按 `AGENTS.md` 和 `docs/INDEX.md` 完成阅读路由；命中已有记录类别时，先读原记录再操作。
2. GUI 图集修改前必须从目标版本实际渲染入口核对 UV、宽高和偏移，素材路径须先核对 JAR 条目，不能从物品名称或外观推断。结论必须来自真实代码、资源、JAR、日志、工具结果或上游资料；未经验证的推测不得作为实现依据或经验写入。判断模组支持的 Minecraft/加载器版本时，必须读取目标 JAR 的 `mods.toml`、`fabric.mod.json` 或等价元数据中的实际版本范围；文件名、下载页标题和构建后缀只能用于定位文件，不能单独作为版本不兼容或冲突证据。
3. 动手前确认 Git 工作树并保护既有改动；修改范围只覆盖当前任务，不能顺手清理无关内容。最终构建前必须逐项审查 `git diff --name-status` 和未跟踪文件，所有二进制差异必须单独核对来源与需求归属；任务外文件不得进入最终构建产物。
4. 发现规范错误后立即停止扩大影响，先恢复正确路径，再完成“记录、固化防线、验证”闭环。
5. 同类错误复发时必须升级原防线；重复同一句提醒、只说“以后注意”或另建重复记录均不算闭环。
6. 跨模组复用上游翻译键时，必须从目标版本的实际语言资源逐字核验键名与占位符；不得按命名习惯拼接或猜测。若无法取得目标语言资源，则不实现依赖该键的显示，先报告阻塞。
7. 编写更新日志时，先以上一个有发行包、发布记录或用户确认可核对的公开发布版本为基线判断条目性质；版本号、标题日期、仓库提交、未分发构建、开发日志和同一版本的持续整理都不是发布证据。同一未公开功能已有条目且原描述仍准确时，开发期完善只写实现文档，不再次扩写日志；只有原描述冲突、遗漏关键功能边界或事实错误才修改。未公开功能内部修正不得单列为 `调整内容` 或 `修复内容`；非关键视觉、资源和内部实现细节不写日志，也不改变标题日期或发布类型。
8. 更新日志固定维护在项目根目录 `CHANGELOG.md`，仅维护中文版本日志；该文件只保留版本元数据和日志条目，具体编写要求统一写在 `docs/changelog-guidelines.md` 中；版本号未修改时，涉及关键内容的更新写入当前版本号条目，非关键视觉、资源或实现细节不修改日志，不建立“未发布”区段。
9. ICEcore 新增的外部模组兼容、扩展或行为修改在更新日志中归入 `新增内容`；`调整内容` 仅用于 ICEcore 已有内容的行为、规则、表现或配置调整。更新日志不使用 `兼容性` 分类，外部模组名称只作为功能适用场景描述。
10. 更新日志不维护英文版；版本信息、分类和玩家可见描述均使用中文，模组名、技术名、版本号和许可证标识等专有名称按原文保留。
11. 更新日志正文只保留版本日志，不嵌入格式说明、维护规则或文档介绍；规则统一写入 `docs/changelog-guidelines.md`，涉及更新日志的任务必须先读取该文档。
12. GitHub Wiki 必须使用 GitHub 原生 Pages 导航，首页文件固定为 `Home.md`，其它页面文件放在 Wiki 仓库根目录；不得添加 `_Sidebar.md`，以免替换并隐藏 Pages 导航。页面名称由 GitHub 显示，正文不得重复同名一级标题；`内容` 页面不增加“功能”等总板块标题，说明文字后直接按功能列出长期有效条目，各项内容使用 `###` 级别标题，不使用更新日志的版本/日期结构。只有新增或改变长期使用说明时才维护相关 Wiki 页面，长期使用说明包括操作步骤、命令、权限、配置字段、文件位置、生效方式和必要限制；纯视觉表现、渲染方式、内部实现、性能修复和开发期 bug 修正不写入 Wiki。不写代码、实现链路、验证细节或开发过程。连续列出多条指令时必须使用“命令｜作用”列表或表格逐条说明，不得只堆叠无说明的命令代码块。
13. 涉及外部模组 UI 反馈时，必须从目标版本字节码确认反馈字段是“状态”还是“事件”，并盘点所有产生同一玩家行为的入口（原生点击、拖放、快捷操作及兼容层入口）；对按下/释放或拖拽等多阶段输入，必须逐阶段确认兼容层取消事件能够阻止原版后续处理；连续相同结果需要由带结果的客户端事件包或等价事件序号直接触发反馈，并避免服务端状态同步与客户端事件处理同时触发同一音效。

14. 实现或记录任何功能时，必须把性能开销作为硬性准则；先识别 tick、渲染、频繁事件和大规模数据处理等高频路径，限制重复扫描、反射、同步 I/O、对象分配、网络包和日志的频率，并在验证中确认不会因主线程负担或无界工作造成卡顿。

### ERR-20260826-06：只拦截客户端 tick 与容器 Open 事件导致冒险物品丢弃动画和待恢复栈不稳定

## 写入判定

满足以下任一条件时，必须记录为“规范错误”：

- 违反本项目 `AGENTS.md`、索引路由、目录边界、Git、编码、验证或文档维护要求。
- 使用了错误事实、API、版本、路径、工具或假设，已经产生错误结果或存在明确风险。
- 越过用户授权范围、覆盖既有改动、遗漏强制验证，或由用户明确指出工作方式错误。
- 已有防复发规则覆盖该问题，但同类问题再次发生。

同时满足以下条件时，才记录为“经验”：

- 有真实证据支持，而非猜测或仅凭记忆。
- 能清楚说明适用场景和不适用边界。
- 能转化为以后可执行、可检查的做法。
- 对未来任务有复用价值，不是一次性过程细节。

纯排版修正、当场纠正且无外溢风险的输入失误、无复用价值的过程流水账不单独记录。若它们暴露出规则或检查缺口，仍应按规范错误记录该缺口。

## 强制闭环流程

1. **止损**：停止继续沿用错误前提，确认影响文件、命令、产物和工作树状态；不以删除用户改动的方式恢复。
2. **查重**：按错误类别、触发条件和防线搜索现有编号。同类问题更新原记录，不新建措辞不同但实质相同的条目。
3. **记录事实**：写清触发场景、可核对证据、根因和影响；事实与推断分开表述。
4. **纠正结果**：完成当前任务中的实际修复，并说明正确做法。
5. **固化防线**：至少落到一项未来会触发的载体，如 `AGENTS.md`、`docs/INDEX.md` 阅读路由、专题文档、自动检查、测试或构建命令。单独写“注意”“谨慎”无效。
6. **验证防线**：执行最窄且能证明结果与防线都有效的检查，记录命令或人工核对点及结果。
7. **关闭**：仅当纠正结果和防复发措施均已验证后，状态才能由“处理中”改为“已关闭”；有残余风险时保持“观察中”。

## 复发升级规则

- 同类问题的判断以根因和失效防线为准，不以表面报错文本或涉及文件是否相同为准。
- 复发时在原记录增加复发次数、日期、最新证据、原防线失效原因和升级措施。
- 升级后的措施必须强于原措施。例如“文档提醒”复发后，应升级为强制开工路由、可运行检查、测试或构建门禁，而不是换一种提醒措辞。
- 复发记录不得沿用旧验证结果；必须重新验证升级后的防线。
- 同一问题第二次复发后，必须优先采用自动化检查或硬性门禁；确实无法自动化时，要记录原因并设置明确的人工检查点。

### EXP-20260822-02：客户端渲染隐藏状态在 tick 更新会与逐帧渲染错拍导致闪烁

- 类型：经验
- 状态：观察中
- 首次发生：2026-08-22
- 最近复发：2026-08-23
- 复发次数：4
- 触发场景：扳手拆除预览用 `BuildingClientRenderState` 隐藏坐标把原方块从异步区块网格移除。用户反馈切换拆除目标、以及放置方块后（无论成功与否）预览会有一瞬间晃眼闪烁。
- 事实证据：`BuildingClientEvents` 原在 `onClientTick`（`TickEvent.Phase.END`，20Hz）调用 `refreshHiddenRenderState` 更新隐藏集，而 `onRender`（`RenderLevelStageEvent.Stage.AFTER_PARTICLES`，60Hz+）逐帧渲染预览并用同一命中目标；`BuildingClientRenderState.update` 通过 `setBlocksDirty` 触发**异步**区块重建。放置路径 `onRightClick` 设 `suppressPlacementPreviewTicks=3` 后要等下一 tick 的 `isPlacementPreviewSuppressed` 才 `clear()` 隐藏集。
- 根因：隐藏集更新（tick）与预览渲染（帧）节奏不一致——切换目标时某帧准星已到新目标，但上一 tick 的隐藏集仍指向旧目标，旧方块已从网格移除却无预览覆盖，短暂变成“缺方块”缺口（最晃眼）；放置时放置位置仍留在隐藏集，原版放置后的区块重建把新方块按隐藏状态重建（先不可见），下一 tick 清隐藏集再触发第二次重建才弹出。
- 影响：拆除目标切换和放置后出现晃眼的方块缺口/弹出闪烁，影响观感；异步重建的固有延迟会放大该错拍窗口。
- 正确做法：渲染用目标仍在渲染路径逐帧计算，但“期望目标”和“已提交可见目标”必须分离。区块构建任务捕获不可变隐藏快照；新目标 section 上传后才增加对应预览格，旧目标 section 恢复后才撤下对应旧预览格，跨 section 多格结构逐格满足“原网格或预览恰好一个”。快速扫动用串行的最新目标队列与代次丢弃过期完成通知，不同步编译区块。放置抑制窗口仍仅在 `allowed` 时启动。
- 防复发措施：保留逐帧目标计算与有效放置抑制规则；新增 `BuildingClientRenderState` 两阶段事务、Vanilla/Embeddium 上传完成屏障和按 section 覆盖集合。第 21 条升级为强制检查任务级快照、代次、快速扫动队列、进入/切换/离开及跨 section 多格结构，不再把异步闪烁列为可接受代价。
- 验证：Forge 47.4.10 `compileJava` 与 `clean build` 通过；用实际映射 JAR 核对 Vanilla 上传、CompiledChunk 与 `addRecentlyCompiledChunk` 时序，用整合包 Embeddium 0.3.31 JAR 核对 `WorldSlice.copyData`、`ChunkBuildOutput`、`RenderSection` 和 `RenderRegionManager.uploadMeshes` 签名。源码级推演覆盖进入、切换、离开、快速来回扫动及跨 section 多格结构；仍需用户实机确认，保持观察中。
- 适用边界：适用于 Forge 1.20.1 Vanilla 区块渲染与已核对的 Embeddium 0.3.31；更换渲染器或 Embeddium 主版本必须重新核对任务快照与真实 GPU 上传完成入口。抑制窗口规则仍适用于其它成功操作副作用。
- 关联项：[冒险模式建造系统](content-implementation.md#冒险模式建造系统)、`BuildingClientEvents`、`BuildingClientRenderState`、`RenderChunkRegionMixin`、`EXP-20260822-01`、`ERR-20260820-02`。

### EXP-20260822-01：只写深度加近偏移的遮罩无法与需透出背后地形的半透明预览共存

- 类型：经验
- 状态：观察中
- 首次发生：2026-08-22
- 最近复发：无
- 复发次数：0
- 触发场景：扳手拆除预览曾采用“`AFTER_SKY` 只写深度遮罩 + `AFTER_PARTICLES` 半透明可见模型”两阶段渲染，为盖住异步区块重建过渡帧的原方块旧网格；用户对比放置失败预览（半透明、透出真实草地）反馈扳手预览整块呈不透明天空色、空白处仍是天空色。
- 事实证据：`BuildingClientEvents` 曾定义 `WRENCH_PREVIEW_DEPTH_MASK_RENDER_TYPE`，用 `WRENCH_PREVIEW_LAYERING`（`RenderSystem.polygonOffset(-1.0F, -10.0F)`）把深度推近相机、`WriteMaskState(false, true)` 只写深度，在 Forge 47.4.10 `LevelRenderer` 的固体区块层（`AFTER_SKY` 之后、`AFTER_PARTICLES` 之前）绘制前占用目标深度。第一次尝试让可见模型匹配同一偏移（`WRENCH_PREVIEW_MODEL_RENDER_TYPE`）后模型可见，但用户两张对比截图证明仍与放置失败预览观感不同：扳手预览的半透明与天空混合而非与地形混合。`RenderChunkRegionMixin` 的 `m_8055_` 注入已把隐藏坐标返回空气，原方块本就不在异步重建后的新网格中。
- 根因：只写深度且用 polygon offset 把深度写到“比真实表面更近”的遮罩，会让固体区块层里目标背后的全部地形（地面、相邻方块）`lequal` 深度测试失败被剔除，这些像素只剩 `AFTER_SKY` 阶段的天空色；随后 `AFTER_PARTICLES` 的半透明模型只能与天空混合，深红 α0.62 叠天空 = 粉红且“看似不透明、透出天空色”。“遮蔽背后一切”与“半透明要透出背后真实地形”在深度语义上互斥，无法通过调可见模型偏移调和。放置失败预览渲染在空气位置、无遮罩，直接与真实地形混合，故正常。
- 影响：扳手拆除预览与放置失败预览观感严重不一致，玩家无法获得一致的深红半透明提示；上一轮“可见模型匹配遮罩偏移即可”的思路被证伪，属于同一“遮罩物理矛盾”未识别的连续两次改动。
- 正确做法：当半透明预览需要透出目标背后真实地形时，不使用只写深度加近偏移的遮罩；依赖 `RenderChunkRegionMixin`/Embeddium `WorldSlice` Mixin 把原方块从异步区块网格移除来避免稳态重叠，可见模型直接复用放置失败预览的 `RenderType.translucent()` 在真实深度与真实地形混合。移除 `WRENCH_PREVIEW_*` 遮罩常量、`renderWrenchPreviewDepthMask`/`renderDepthMask` 与 `AFTER_SKY` 分支，`renderWrenchPreviewModel` 调 `renderInvalidPreview(..., RenderType.translucent(), INVALID_PREVIEW_ALPHA)`。可接受的代价：准星切到新目标后、异步重建完成前的 1~2 帧内原方块短暂带红显示（经用户确认接受）。
- 防复发措施：`docs/content-implementation.md` 冒险模式条目实现链路与最后修改字段改记“无遮罩、复用 translucent、原方块由 mixin 从网格移除、1~2 帧过渡带红”；“生效中的防复发规则”第 20 条改为“只写深度加近偏移的遮罩会剔除背后地形，与需透出地形的半透明预览互斥，此类预览不得叠加此类遮罩”；本条与 ERR-20260820-02 的“扳手保留一个前置深度遮罩批次”防线冲突，已在该记录中标注废止该子防线。
- 验证：`gradlew.bat compileJava` 通过（仅 deprecation 提示）；已用 decompile 源码核对 `RenderType.translucent()` composite state（无 layering、`lequal` 515、`COLOR_DEPTH_WRITE`）；已确认 `RenderChunkRegionMixin` 通过 `m_8055_` 返回空气隐藏原方块，稳态不依赖遮罩；扳手预览与放置失败预览一致性及过渡帧表现需用户在客户端确认，保持观察中。
- 适用边界：适用于 Forge 1.20.1 客户端“半透明预览需透出目标背后真实地形”的场景；若目标是完全不透明预览、或确实需要遮蔽背后一切，则遮罩仍适用，不受本条约束。原方块隐藏依赖异步 mesh 重建，故过渡帧不可避免，除非改用同步区块重建（会引入准星移动卡顿，违反性能准则）。
- 关联项：[冒险模式建造系统](content-implementation.md#冒险模式建造系统)、`BuildingClientEvents`、`RenderChunkRegionMixin`、`ERR-20260820-02`。

### ERR-20261001-01：禁食最终拦截误伤烧烤串制右键

- 类型：外部模组交互兼容回归；状态：已修正。

### ERR-20261001-02：通用禁食前置拦截误伤食品材料交互

- 类型：通用交互边界设计错误；状态：已修正。
- 触发场景：ICEcore 在客户端输入事件或 `MultiPlayerGameMode.useItem` 入口按手持食品提前取消右键，导致食品作为串制材料、料理台输入或容器内容时无法交给外部模组处理。
- 事实证据：Forge 1.20.1 的 `LivingEntityUseItemEvent.Start` 是物品真正开始持续使用的语义事件；此前两个客户端前置拦截点在外部模组右键处理完成前执行。

- 影响：不同外部模组需要不断增加专用白名单，且仍可能因事件顺序差异漏放或误拦。
- 正确做法：通用禁食只在 `LivingEntityUseItemEvent.Start` 取消真正开始的使用；客户端不再按食品类别取消输入或 `useItem`，让外部模组先消费右键。客户端在 Start 仅记录拒绝；LocalPlayer.startUsingItem RETURN 才清理被后置赋值覆盖的标志，并精确跳过同次拒绝引起的 itemUsed 高度归零。
- 防复发措施：食品兼容代码禁止新增输入事件或 `MultiPlayerGameMode.useItem` HEAD 的通用食品拦截；禁止在 Start 内调用 stopUsingItem 并假定已清理 LocalPlayer；必须核对调用返回后的赋值和渲染反馈；新增模组兼容先确认其是否进入 `Start` 事件，只有绕过该事件并直接修改饥饿值的模组才单独适配。
- 验证方法：源码契约测试断言客户端食品前置拦截和 `m_233721_` 注入不存在，并断言 Start 只记录、LocalPlayer RETURN 清理与 itemUsed 反馈条件抑制；执行定向食品测试、完整构建，并实测串制、投料、容器交互与普通直接进食无一帧动画。
- 适用边界：绕过原版持续使用、在自定义 `use` 中直接扣物品或修改饥饿值的第三方实现仍需独立按真实 API 适配。
