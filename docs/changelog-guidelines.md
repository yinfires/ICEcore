# ICEcore 更新日志编写要求

本文是 ICEcore 更新日志编写与维护规则的唯一详细说明。编写、修改或审查更新日志前，必须先读取本文，再读取根目录 `CHANGELOG.md` 的当前版本条目。

## 文件职责与位置

- 更新日志固定维护在项目根目录 `CHANGELOG.md`，`docs/` 内不创建副本。
- `CHANGELOG.md` 只保留版本元数据和实际日志条目，不写格式说明、维护规则或其它文档介绍。
- 本文只记录更新日志的编写要求；具体实现事实仍写入 `docs/content-implementation.md`。

## 语言与表达

- ICEcore 更新日志只维护中文版本，不另写英文版。
- 版本信息、分类和玩家可见描述使用中文；ICEcore、CozyCafe、JEI、Forge、版本号和许可证标识等专有名称按原文保留。
- 使用客观、面向玩家、结果导向的描述；仅在说明功能适用条件时提及相关模组，不写内部类名或实现过程。

## 版本条目格式

- 新版本条目追加在旧版本上方。
- 每个版本记录版本号、发布日期、Minecraft 版本、模组加载器、许可证和发布类型。
- 发布类型和日期必须随当前版本内容实时维护：只有 Forge 加载骨架时才使用“开发骨架”；一旦条目包含玩家可用功能，就改为准确概括当前内容的类型，当前条目应使用“功能更新”，不得沿用过时类型。
- 当前版本仍在持续整理时，标题日期使用本次关键内容的最后修改日；仅发生非关键的视觉、资源或实现细节调整时，不更新标题日期或发布类型。确定对外发布后改为实际发布日期，并在后续仅做文字润色或非关键内容维护时保持发布日期不变。标题日期、版本号或“功能更新”发布类型都不等于已经对外发布，不能单独作为修复条目的资格证明。
- 分类按需使用：`新增内容`、`调整内容`、`修复内容`；没有内容的分类直接省略。
- 版本之间使用单独一行 `——————` 分隔。
- 不建立“未发布”区段。

## 版本号与内容归属

- `gradle.properties` 的 `mod_version` 是当前构建版本的唯一权威来源。更新日志最上方版本必须与它完全一致；若构建版本高于当前日志顶部版本，必须在旧版本上方新增版本条目，保留旧版本原有标题和历史内容，禁止通过改写旧标题把旧版整体冒充为新版。
- 版本号未修改时，涉及关键内容的新增、调整和修复继续写入当前版本号条目；仅发生非关键视觉、资源或实现细节调整时不修改日志。只有版本号修改时才新增版本条目。版本号相同不代表新增内容已经发布，也不代表开发期间的修正可以单列。
- 每次版本记录以上一个明确公开发布版本为比较基线，覆盖从上次版本变更以来的关键玩家可见改动、修复与更新；“明确公开发布”必须有可核对的发行包、发布页面、发布记录或用户确认作为证据，仓库提交、未分发构建、开发日志、实机测试和同一版本号的持续整理均不构成发布基线。
- 只让本次尚未公开发布的新增功能达到正确状态的修正，必须合并进对应的最终 `新增内容` 描述；即使修正发生在同一版本号下、已经被标记为“功能更新”、已经写入实现文档，或玩家在开发环境中看到过错误，也不得另列为 `调整内容` 或 `修复内容`。
- 同一未公开功能已有日志条目且原描述仍与最终行为一致时，开发期完善不得再次扩写或改写该条目；只有原描述与最终行为冲突、遗漏关键功能边界或需要纠正事实时才修改。视觉稳定性、内部实现和不改变既有功能承诺的缺陷消除只写实现文档。
- 只有能证明问题已经存在于上一个明确公开发布版本，且本次版本改变了玩家相对该已发布版本可观察到的行为时，才单列为 `修复内容`；若无法提供基线证据，按未发布新增功能内部修正处理并合并描述。
- 当前模组新增的外部模组兼容、扩展或行为修改归入 `新增内容`；外部模组名称只作为功能适用条件写入条目正文，不改变分类。
- `调整内容` 仅用于 ICEcore 已有内容的行为、规则、表现或配置调整；对外部模组现有行为进行新增兼容、扩展或修改时，不得归入 `调整内容`。
- 不使用 `兼容性` 分类；分类依据是 ICEcore 是否新增或调整玩家可见内容，而不是功能是否依赖其它模组。
- `CHANGELOG.md` 只记录相对公开基线的关键玩家可见变化和版本元数据。同一版本已有新增内容的持续整理中，只有涉及功能增删、命令/权限/配置、核心规则或适用范围、兼容行为、重要玩家可见行为，或需要纠正日志事实的改动，才更新当前版本条目。
- 贴图、图标、模型资源、颜色/排版等非关键视觉调整，以及内部实现细节和开发期清理，不写入更新日志；这类改动只在 `docs/content-implementation.md` 等实现文档中记录，也不改变更新日志标题日期或发布类型。

## 编写检查

1. 读取 `gradle.properties` 的 `mod_version`，确认它与 `CHANGELOG.md` 最上方版本一致；若版本号已提高，在旧版本上方新增条目并保留旧版历史，不得直接改写旧版标题。再选择当前版本条目；不要把版本号或标题日期当成公开发布边界。
2. 先判断改动是否触及关键内容；如果只是贴图、图标、模型资源、颜色/排版等非关键视觉调整，或内部实现细节，则只更新实现文档，不修改 `CHANGELOG.md`、标题日期或发布类型。
3. 记录上一个明确公开发布版本的证据（发行包、发布页面、发布记录或用户确认），逐条检查该功能/问题是否在该基线中真实可用或可遇到。
4. 对没有基线证据的新增功能、开发期问题和同一版本内修正，先检查已有新增条目的事实是否仍成立；成立则不修改日志，只更新实现文档。仅当原描述冲突、遗漏关键边界或事实错误时才修改已有条目，不得为了记录完善过程叠加细节。
5. 只有通过基线证据检查的问题才允许进入 `修复内容`；在条目草稿旁保留“基线证据”和“相对基线的玩家可见变化”两项核对结果，无法回答任一项就退回合并处理。
6. 根据最终关键内容实时更新标题日期和发布类型，再将玩家可见结果写入中文日志，补齐其余版本元数据和需要的分类；非关键改动不触发元数据更新。
7. 逐条确认：外部模组兼容、扩展或行为修改属于 `新增内容`；只有 ICEcore 已有内容的修改才属于 `调整内容`；同一未发布新增功能的修正不属于两者中的独立条目。
8. 确认 `CHANGELOG.md` 中没有规则说明、英文版、未发布区段或兼容性分类，并扫描是否存在“修复/调整”条目却没有对应公开基线证据。
9. 使用显式 UTF-8 回读更新日志，并检查根目录文件可被 Git 跟踪、旧 `docs/CHANGELOG.md` 不存在。
