# MC 贴图与模型制作流程

Last updated: 2026-09-08

适用于 ICEcore 工作区发起的 MC 物品、方块、GUI 贴图与 Blockbench 模型制作。目标是先确定可读的造型和配色，再得到尺寸、UV、依赖与导出格式正确的正式资产。只规划流程不代表已接入模组。

## 任务规格与文件位置

- 先核对用途：独立概念图、二维物品贴图、方块贴图、GUI 图集或三维模型；确认目标游戏/加载器/模型格式。ICEcore 默认 Minecraft 1.20.1 Forge，不把其它版本格式直接套用。
- 从实际资源、JAR 或已存在项目取得原始尺寸、命名空间、纹理引用、GUI 裁切参数及模型格式。用户指定参考优先；精确还原时不以生成图替换指定素材。
- 记录预期轮廓、配色、实际显示尺寸、透明需求、变体、应保持不变区域及几何/纹理预算。默认沿用原资源像素密度；无基准时从能表达形状的较低分辨率开始，不把高分辨率参考直接当作高分辨率游戏贴图。
- 新任务统一保存到 `D:/Minecraft/Mod Develop/模型/<任务名>/`，包括独立 MC 贴图任务。可按需创建 `reference/`、`source/`、`export/`、`preview/`、`scripts/`；不创建空目录。工程、源 PNG、UV 图及脚本均在此任务目录。规范、来源、决策和验证记录只写 ICEcore 的 `docs/`，不在资产目录散放开发文档。
- 不自动搬迁或删除历史产物。正式接入时仅复制构建必需内容至资源树；参考图、bbmodel、预览和生成脚本不进入运行时资源包，除非某文件确为所选运行时格式所需。

## 参考图与视觉方向

- 已有用户指定的碗盘来源先锁定实际资产，不得仅参考比例后自行重造。容器几何、UV 和原贴图最近邻像素等效必须进入来源比对门禁；仅调整食物以适配容器。生成图不得覆盖此约束。

1. 新造型或风格探索可先调用 `gpt-image-2` 生成一张参考图，按全局 `gpt-image-2-api` 技能复用当前 API。此步骤已获用户长期偏好支持；若用户指定禁用生成图、已有完整参考或只是修补几个像素，则跳过。
2. 提示词明确主体、MC 风格/目标像素密度、轮廓、材质、配色、背景、视角及禁止变化。模型参考需要判断厚度或内外结构时可补正面、侧面、俯视或底面；各视图可能不一致，不能机械反推尺寸。
3. 首张以低成本验证方向，通常请求 1024×1024、medium；确有细节需求再调整。保存实际返回图并核对其实际尺寸，不把请求参数当作文件事实。
4. 从参考提取有限色板、轮廓、材质层次和比例，转为可执行规格。透视、光影、纸张纹理、伪像素和不一致结构均需在正式制作中处理。
5. 自行完成一般选择并推进。仅当参考之间存在影响用途的矛盾或缺少关键规格时询问用户；API 不可用时说明原因，有足够参考则继续正式制作，不悄悄换模型。

## 参考转化与视觉质量门禁

这些检查适用于每次新制作和用户反馈后的修订，属于执行流程；只补文字而未检查当前成品不算完成。

1. **先定义可见特征。** 制作前在对应实现条目记录参考的轮廓、边框比例、材质、配色层次和留白，以及它们在成品中的位置与实现方式。至少覆盖本任务真正影响观感的特征，不以固定条数充数。生成参考图后，不能沿用旧绘图脚本换色便宣称参考已落实。
2. **按任务选择制作手段。** 适合保留的生成材质可裁取、清理、量化后使用；需要严格像素形状的边框与 UV 单独制作。也可重绘，但必须在参考/成品同尺度对照中保留目标特征。裁片须检查是否混入边缘、阴影或接缝；每个格槽使用局部坐标，避免按全图取模造成内部断线。提取材质不自动等于质量提高。
3. **验证屏幕坐标。** 分开记录图集切片矩形、游戏绘制偏移、实际有 alpha 的边界、物品内容矩形。将实际偏移代入合成后验证：高亮围住本格、边界按设计对齐、中心不遮住内容、不越过邻格；切片尺寸正确不能证明视觉边框正确。偏移与缩放必须来自真实消费端。
4. **检查无修饰的成品。** 先看原尺寸和最近邻放大图，再看展示排版。GUI 至少检查空格、实际物品填充、首/中/末选中，按范围补左右副手、hover 等状态。预览从最终导出图集裁切，并使用真实坐标与叠放顺序；不能用物品、宣传文案或大图缩放掩盖缺陷。
5. **检查材质与秩序。** 逐项检查边框粗细、转角、间距、明暗方向、槽内接缝、重复周期、低对比纹理与物品可读性。细节应能说明材质结构；无依据的短线、随机点、高光块或规则重复装饰先移除。平整边缘应连续；若设计本来需要纹理变化，应定义允许区域与对比度，而不是强行全图单色。
6. **把缺陷变成检查。** 可量化问题加入当前资产生成/验证脚本：实际位置后的 alpha bounds、保护区差异、透明中心、边缘连续性等。脚本覆盖有意义的输出不变式，不能只断言绘图参数。主观材质质量仍需看图，不用像素断言宣称审美已通过。
7. **失败就返工。** 导出后必须实际打开成品；发现新接缝或其它问题，当轮修正并重新检查受影响状态。最终分别说明技术验证、视觉检查和游戏实测边界；用户尚未认可时不得写“审美验收通过”。重复问题更新已有经验的复发证据、原防线失效原因和升级措施。

## 二维贴图执行步骤

1. 在目标像素尺寸下建立 RGBA 画布，先画轮廓与主要色块，按实际游戏显示大小检查可辨识性，再加高光、阴影和少量材质细节。
2. 像素风保持像素网格、边缘和色板一致；预览放大用最近邻，避免缩放引入模糊、透明边缘杂色或额外颜色。高分辨率生成图需要重新整理像素，缩小一次不等于完成贴图。
3. 方块的平铺面检查重复拼接与各面的像素密度；GUI 图集按真实消费端的 UV、裁切宽高、九宫格/拉伸规则作图，未修改区域逐像素保持不变。
4. 变体先定义允许修改的像素区域，再绘制污渍、磨损或配色；用差异图确认变化全部落在允许区域内。贴图需要透明时检查真实 alpha，棋盘格背景不是透明。
5. 动态贴图仅在需求要求时增加；核对目标版本的帧尺寸、顺序、时长及 `.mcmeta`，同时核算全部帧资源成本。

## 三维模型与 UV 制作

器皿类型先独立判定，不能从配方 carrier 或返还的 bowl 推断。盘强调浅腹、低侧边和可见盘沿；碗强调深腹与明显侧壁。生成参考前将用户指定类别和真实外观证据写入任务规格，并在正侧视验收检查厚度、口径和盘沿留白。具体比例按任务确定，不把统一配方容器当作视觉依据。

物品 ID 驱动任务先执行 [物品建模能力尝试流程](item-modeling-pilot.md)，并查询 [模型参考源目录](model-reference-library.md)。默认容器与食物的完整几何（含旋转后顶点）位于 0–16 的一格范围内；小菜无需填满整格。参考目录随实际核验更新，不能将候选参考标为已完成复用或视觉验收。

1. 读取实际项目/目标 JAR，选择兼容的 Blockbench 工程与导出格式；先做低复杂度灰模，确定尺寸、原点、朝向、厚度、轮廓及显示变换，不凭模型名称猜结构。
2. 按几何位置和朝向建立语义面表，例如内壁、外壁、沿口、内底、外底。表中至少记录元素/面、纹理、UV 像素区、可共享对象及是否受保护。
3. 展开 UV 后再绘制局部纹理。需不同颜色或保持干净的面分配独立纹理或带间隔的 UV 岛；共享像素必须是明确设计，禁止污渍污染外壁等保护面。
4. 统一 PNG 尺寸、项目 UV 分辨率、每纹理 UV 尺寸与目标导出规范。Java block/item JSON 的 UV 按 0–16 归一化核算；其它格式按其实际规范，不套用同一规则。
5. 优先用少量有意义的几何表达轮廓，用贴图表达细节；删除确定不可见且不影响预期用途的冗余面，避免重叠面闪烁，不为局部污渍堆叠透明几何。
6. 保存可编辑工程及自包含纹理，导出游戏模型和独立 PNG。逐一核对纹理引用路径，不能让交付依赖桌面绝对路径或本机临时文件。

## 验收与返工条件

- **发光方块拼接的光照门禁**：统一材质的相邻方块中包含炉灶等光源时，静态编辑器预览不代表游戏亮度一致。实现前核对真实 Forge 和当前渲染后端的 AO 模式选择、材质发光亮度下限、遮蔽缓存及面采样入口；用户要求表面不额外发亮时，仅修改目标材质渲染采样，不改变世界发光/传播。自动检查实际调用点、依赖缺失和注入冲突；实机须覆盖昼夜、AO开关、点燃/熄灭与混合排列。未授权启动时明确保留待验项，不以UV/像素测试或Blockbench图替代。来源与防线见 `workspace-errors-and-lessons.md` 的 ERR-20260908-03 光照补充。

| 对象 | 必须检查 | 通过条件 |
| --- | --- | --- |
| 参考图 | 文件解码、实际宽高、主体与风格 | 说明其参考用途，未误作最终贴图 |
| PNG | 尺寸、格式、alpha、色板、像素边缘 | 符合目标规格，无意外背景或糊边 |
| 图集/变体 | 实际消费范围、差异像素、保护区域 | 无越界，保护区域逐像素不变 |
| 模型 | 元素/面数量、方向、UV、纹理依赖 | 无 UV 越界或非预期重叠，语义面绑定正确 |
| 工程与导出 | 在空项目重新导入最终文件 | 工程与游戏导出分别核对，无缺失纹理或结构差异 |
| 视觉 | 正面、侧面、俯视、底面、UV 编辑器 | 内外面及底部都可核验；按用途检查持握/GUI 显示变换 |
| 性能 | 几何面数、纹理尺寸/张数、动画帧、透明层 | 与需求相称；静态资产不引入 tick、网络或运行时生成 |

- 模型验收脚本可参考历史 `tool/verify_bowl_uv.py` 的检查思路；其碗模型的元素数量、UV 区域和预期结果不得用于其它模型。新模型专用脚本放任务目录 `scripts/`。
- 纹理基础 RGBA 内存按宽×高×4×张数估算，另考虑 mipmap、动画和运行时实现；按实际用途约束面数与透明过绘，不给所有资产武断使用同一面数上限。
- Blockbench 优先采用已配置的 MCP：先核对配置、initialize、tools/list 及一个只读调用，再编辑；工具入口缺席不等于程序不可用。重导入前保护当前未保存工程，优先新建隔离工程。
- 若编辑器不可用，可先完成文件/UV 静态检查，但必须标出重导入与视图检查尚未完成；不得把静态合成图说成编辑器或游戏截图。
- 任一保护面、纹理绑定或导出重导入检查失败，先修正再交付；记录真实残余限制。用户指出的问题按工作区经验规则查重、升级防线。

## 接入与交付

- 独立资产任务：交付可编辑工程（若有）、最终模型/贴图、必要 UV 图及多视角预览，明确绝对路径、实际尺寸、几何数量、纹理依赖、已完成与待完成验收。不因制作参考资产自行修改模组实现。
- 正式接入任务：检查命名空间及模型/纹理/方块状态引用，根据需求维护资源、语言与实现文档，确认构建文件可被 Git 跟踪，参考和工作文件仍在本地目录。
- 验证按范围执行：文档规划仅检查链接与规则；独立资产执行格式、UV 和重导入检查；模组接入先做窄验证，再按工作区规则运行 Forge 47.4.10 基线 `gradlew.bat clean build` 并检查资源展开与 JAR 内容。结构改动后核对 CodeGraph 状态。
- 不自行启动 Minecraft、PCL 或 `runClient`。游戏实测只有用户明确授权后执行；此前将光照、持握或运行时渲染等未验证项列清楚。
- 每次实际制作或修改更新 `docs/content-implementation.md` 对应条目。纯视觉细化不写版本日志或 Wiki；关键玩家可见变化及长期使用说明分别遵循各自维护规则。

### 铺盘菜覆盖检查

用户指定铺满的菜品，食材覆盖除最外围一原始纹理像素外的整个盘面；先用真实 PNG 尺寸、盘顶 UV 与几何求像素宽度，不按放大的工程纹理误算。俯视检查边角和内部空洞，侧视检查食材厚度；不能只放大酱汁平面充当丰满度。具体非铺盘菜不强套此规则。
