# 物品建模能力尝试流程

用途：把物品 ID 转化为可核对的外观解释、三视图和可编辑模型。2026-09-08 首个样例为 `kaleidoscope_cookery:scramble_egg_with_tomatoes`。已完成盘装初版文件与编辑器重导入；用户审美与游戏实测尚未确认。

## 默认规格

- Minecraft 1.20.1 Java 静态物品模型，优先 Blockbench Java block/item 格式；交付 bbmodel、JSON、PNG、UV 和导出多视角预览。
- 包括碗盘、食物和旋转后的全部顶点，X/Y/Z 均在 [0,16] 内。拟以中心 (8,0,8) 放置，按食物实际比例留白；不通过 GUI 缩放掩盖越界。
- 资产放 `D:/Minecraft/Mod Develop/模型/<命名空间>-<物品ID>/`；来源与决策记在本项目 docs。仅在另有接入需求时安装资源或修改模组。

## 四阶段与退出条件

| 阶段 | 实际工作 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1. ID 与原始资源 | 优先 libs，缺失时找本机实例或上游；核对版本元数据、语言名、item model 的 parent/纹理引用和 PNG，识别覆盖资源与内置可选资源包；记录指纹 | 精确 ID、版本、模型链和原图已确认；缺资源时只询问缺失来源，不猜路径 |
| 2. 外观解释 | 看原图与最近邻放大图；读取所有输出该物品的默认配方，区分食材、工具、燃料；carrier 不用于器皿分类；按区域位置建立“色块→候选含义→证据→置信度”表 | 容器、主食材和轮廓有可执行解释；无法确认的配料保持待定，不强行实例化 |
| 3. 三视图 | 用已确认的原图、现成模型造型依据与色块解释调用 gpt-image-2，生成同一对象的正面、右侧、俯视正交图；记录提示词、输入及实际输出尺寸 | 三视图外轮廓、容器高度、食材位置和主色一致；矛盾先标注统一尺寸或重做，不能直接照三个冲突视图建模 |
| 4. 建模 | 统一尺寸表→低复杂度灰模→语义面与 UV→像素贴图→导出→空项目重导入 | 一格尺寸、纹理依赖、UV、正/侧/俯/底视图及 UV 编辑器检查完成，参考特征逐项对应；不以生成成功或文件存在代替验收 |

名字与默认配方只提供语义证据。配方可能为玩法平衡省略调料或使用替代品，数量不能直接转成几何块数；明暗色块也不必代表不同食材。存在冲突时写出证据和采用理由，只有影响主体且无法合理解决的歧义才向用户询问。现成参考可自行寻找，也可请用户补充；先复用参考目录，避免每次重新查找。

## 番茄炒蛋样例：已核对事实

- 来源：参考目录 KC-1；语言名为“番茄炒蛋” / “Scramble Egg with Tomatoes”。模型 parent 为 `minecraft:item/generated`，layer0 为 `kaleidoscope_cookery:item/scramble_egg_with_tomatoes`，默认 PNG 为 16×16。
- 默认配方：`data/kaleidoscope_cookery/recipes/pot/scramble_egg_with_tomatoes.json` 为 3 个 `forge:eggs` 和 3 个 `forge:crops/tomato`；`recipes/flex_pot/scramble_egg_with_tomatoes.json` 各 1 个。两者 carrier 均为 `minecraft:bowl`，time=200，stir_fry_count=3。不从这些数值推断最终食材块数。
- `scramble_egg_with_tomatoes_rice_bowl` 是独立物品，当前目标不加米饭。
- JAR 另有 `legacy_pack/` 的同名物品资源，本次仅以默认 assets 原图调查；正式执行前核对是否要求使用实例已启用的资源包外观。
- 原图已提取至 `D:/Minecraft/Mod Develop/模型/kaleidoscope_cookery-scramble_egg_with_tomatoes/reference/original-item.png`，同目录 `original-item-20x.png` 是最近邻放大观察图。

| 原图可见区域 | 解释与置信度 | 成品可见特征映射 |
| --- | --- | --- |
| 中部及上部红、橙红、浅红块 | 番茄主体与受光/切面，高；配方与名字互证 | 少量有厚度的不规则番茄块，红色为主，不把每个高光都建成独立块 |
| 中央大块及两侧黄色/浅黄色 | 炒蛋，高 | 分散的黄色蛋块，与番茄交错；避免做成整颗煎蛋 |
| 底部棕褐轮廓与金棕沿口 | 盘子；用户明确指定，配方 carrier 不是造型依据 | 棕金色浅盘，低侧边、可见盘沿，明确盘面与外底；厚度由三视图规格统一 |
| 上部和零星橄榄绿色小块 | 装饰或食材细节，低；默认配方没有葱 | 暂保留为微量纹理色点，不宣称是葱，不新增大块绿色配料 |
| 深红/深棕边缘 | 阴影或描边，中高 | 使用同材质暗色层次；不解释为额外食材 |

## 三视图与模型待执行规格

- 暂定外包围 12×4.05×12 模型单位，底面 y=0，x/z=2..14；这是设计目标，不是原图测量值。先用灰模校正容器与食物比例，再锁定尺寸。
- 图像提示词草案：为 Minecraft Java 物品“番茄炒蛋”制作同一低多边形像素风对象的正面、右侧、俯视正交三视图；棕金色浅盘盛红橙番茄与黄色炒蛋，少量低饱和橄榄绿色纹理点，无米饭、无整颗煎蛋、无餐具与场景；三个视图保持同一尺寸、摆放和配色，干净中性背景，平光，无透视变形；对象完整位于一格方块内。实际生成时附已核验原图，记录最终提示词与工具模式。
- 先比较 KC-1 的盘与紫颂果煎蛋、DD-1 的 food_plate / small_food_plate，炒饭仅参考食物层次，选择容器构造和食物层次的参考，不机械复制其菜品形状。
- UV 语义面至少分容器外壁、内壁、沿口、内底、外底、番茄切面/外表、蛋块；食物污渍不能污染外底。具体 UV 像素区在灰模确定后写入，不提前虚构。
- 静态模型优先少量几何，微小绿色点和明暗用纹理表达。导出统计实际元素/可见面、PNG 尺寸和纹理数量，剔除无用内面与重叠面；不增加 tick、网络、运行时生成。面数预算在参考比较后确定。
- 视觉门禁逐项检查上表特征及三视图一致性；技术门禁检查旋转后包围盒、UV 归一化、共享区域、内嵌纹理与导出路径。在空 Blockbench 工程重新导入最终 JSON 与 bbmodel，检查正/侧/俯/底和 UV。
- 能力尝试分别记录“资源定位、语义推断、生成一致性、几何/UV、重导入视觉”的实际结果和残余问题；未执行项保持未执行。不自动启动游戏，编辑器检查不等于游戏实测或用户审美认可。

## 铺装丰满度修正

用户要求此类铺盘菜覆盖除最外围一像素外的整个盘面。DD tray_top 原图为 16×16，盘顶 UV 1..15 对应模型 1..15，因此一原始像素=一模型单位；128×128 只是最近邻工程图，不按其一个像素计算盘沿。本菜铺装范围 X/Z=2..14，12×12 全覆盖，仅保留外围 1 单位木边。16 块高低错落的番茄/蛋底层补齐边角，原上层继续表达块状层次，不使用薄酱汁面冒充食材丰满度。finalize.py 以 0.5 单位采样验证整个内部区域覆盖；实际编辑器五视图已检查。当前 40 元素、201 面，尺寸和三纹理预算不变。
